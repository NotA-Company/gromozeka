**h2-over-SOCKS5 verdict (2026-08-13, post-migration research — answers design-doc §9 Q2):** SOCKS5 (RFC 1928) is a raw TCP tunnel; h2 is negotiated via TLS ALPN entirely above it — NO protocol incompatibility. Native httpcore 1.x AND httpcore2 have ALWAYS supported ALPN h2 over SOCKS (`httpcore2/_async/socks_proxy.py:243-269`: tunnel → start_tls with ALPN ["http/1.1","h2"] → selected_alpn_protocol → AsyncHTTP2Connection; httpcore changelog 0.14.4 "HTTP/2 on HTTPS tunnelling proxies" Jan 2022 + 0.14.5 SOCKS). The old `"transport" not in proxyKwargs` guard protected against **httpx-socks-era artifacts only**: issue #2 was originally a config misunderstanding (client-level `http2=True` does NOT propagate to a user-supplied transport — maintainer's fix: pass `http2=True` to `AsyncProxyTransport.from_url` itself; closed "working" same day, Mar 2021), plus httpx_socks 0.11.0 has `is_available()` hardcoded `False` (`_async_proxy.py:242`) which breaks h2 connection reuse/pooling. The D3 guard (`useHttp2 = resolvedType != ProxyType.SOCKS5`, yandex_search handler :569) is therefore DEAD WEIGHT on httpx2 native `proxy=`; ALPN falls back to HTTP/1.1 gracefully when the target lacks h2, so `http2=True` over SOCKS is safe even against non-h2 servers. Test `TestHttp2DisabledForSocks5` docstring's "historically-flaky combo" framing is WRONG (it was never SOCKS's fault). **Guard REMOVED 2026-08-13** (post-research follow-up commit): `_downloadUrl` now passes `http2=True` unconditionally; test class renamed `TestHttp2EnabledForAllProxyTypes` (3 methods assert http2 True for SOCKS5/HTTP/NONE, regression-first verified biting); ADR-021 D3 carries the dated removal note; probe smoke closed-by-analysis (Минцифры + Telegram smokes still pending); docs (developer-guide/handlers/design docs) de-claimed the incompatibility.

User asked whether to migrate from `httpx` to `httpx2`. Verdict delivered: **worth it, but incrementally and not urgently.** Durable facts established (all web-verified Aug 13, 2026):

- **httpx2 is REAL** — a legitimate fork under the **Pydantic org** (`github.com/pydantic/httpx2`), NOT encode. Forked from `httpx 0.28.1` commit `b5addb6`; first release `2.0.0` May 12 2026; rapid monthly cadence; trusted publishing + Sigstore. ~900 GitHub stars in 3 months. My initial skepticism ("httpx2 probably isn't real") was WRONG — the `general` agent corrected it. Starlette (encode's own) + MCP Python SDK have already migrated to httpx2.
- **Upstream httpx is stalled** (NOT abandoned): last stable `0.28.1` Dec 6 2024; the 1.0 effort is dev-pre-release-only (`1.0.dev1-3` Jul-Sep 2025) then silent; the "1.0 roadmap?" discussion (#2279) has been Unanswered since Jun 2022. httpx2 cites this stall as its reason to fork.
- **gromozeka is already on the LATEST httpx** — `requirements.direct.txt:9` = `httpx[http2]==0.28.1`, `requirements.direct.txt:10` = `httpx-socks[asyncio]==0.11.0`. So there is NO "ancient version" problem; the user's "not updated for several years" applies to the dep's release cadence, not to our pin. The decision is purely "stay on httpx 0.28.1 vs swap to httpx2 2.x."
- **httpx2 has NATIVE SOCKS** via the `httpx2[socks]` extra (socksio) — `httpx2.AsyncClient(proxy="socks5://...")`. This is inherited from httpx/httpcore, not new. **httpx-socks is droppable for gromozeka-owned clients** (Max, yandex_search, the lib/proxy layer) — replace `transport=AsyncProxyTransport.from_url(url, verify=sslContext)` with `proxy="socks5://host:port", verify=sslContext`.
- **THE single real cost = python-telegram-bot (PTB).** PTB 22.8 owns its own `httpx` clients (`internal/bot/telegram/application.py` passes `HTTPXRequest(httpx_kwargs={...})`; PTB builds `httpx.AsyncClient` internally). Two options: (a) keep `httpx`+`httpx-socks` ONLY for the Telegram subsystem (object boundary — `httpx.Client` vs `httpx2.Client` are different types; don't share request/response objects / `isinstance` / `except` across them); or (b) call `httpx2.alias_httpx()` at the very top of `main.py` before PTB imports to force PTB onto httpx2 process-wide — feasible per the official migration guide but needs a dedicated PTB+SSL test pass because httpx2 switches SSL from certifi → truststore (OS trust store), and Минцифры/Russian-national-CA certs thread through the SOCKS TLS layer (must empirically confirm `verify=sslContext` reaches target TLS through the SOCKS tunnel; httpcore2 #869/#880 fixes make this likely).
- **httpx-sse==0.4.3 is TRANSITIVE, not direct** — present in `requirements.txt:41` but NOT in `requirements.direct.txt`; pulled by `yandex-ai-studio-sdk`; zero `import httpx_sse` in code. Irrelevant to migration. (httpx2 gained built-in SSE `client.sse()` at 2.5.0 and built-in WebSockets `httpx2[ws]` at 2.6.0, if ever needed.)
- **Coupling rated MEDIUM-HIGH by explore, but it's coupling to httpx *internals* that are API-identical in httpx2 (it's a fork from 0.28.1)** — so the custom `AsyncHTTPTransport` subclasses in `lib/aurumentation/` (`RecordingTransport`/`ReplayTransport`), the exception hierarchy (`httpx.HTTPError`/`ReadTimeout`/`RequestError`/`HTTPStatusError`/`TimeoutException`), SSL threading, and `httpx.MockTransport` in tests all port by import-rename. Async-only codebase (no sync `httpx.Client`). ~11 production import sites + ~7 test files.
- **Motivation is maintenance/security velocity, NOT performance** — httpx2 is the same code; perf is equivalent. No reason to switch libs entirely (niquests/aiohttp) — httpx/httpx2 already covers async + HTTP/2 + SOCKS + SSE for this project; a full library swap would be a rewrite for no gain.
- **Recommended path (if user greenlights): incremental.** Phase 1 = migrate gromozeka-owned clients + drop httpx-socks there + verify SSL-through-SOCKS against a real Минцифры endpoint. Phase 2 = decide PTB fate (keep httpx-socks for it, or `alias_httpx()` spike). Treat as opportunistic, not urgent — we're on the latest httpx and nothing is broken.
