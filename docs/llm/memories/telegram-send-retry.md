# Telegram Send Retry (TheBot._retryTelegramSend)

Archived durable notes from [`teamlead-memory.md`](../teamlead-memory.md) (extracted 2026-09-02). See the live compact memory there for cross-cutting rules and workflow lessons.

Added retry to Telegram sends for transient errors. Final: 3939 passed/11 skipped, lint 0/0/0, check-docs 117/2150/0 broken. Branch sits on master working tree.

**What shipped:**
- New private method `TheBot._retryTelegramSend(sendCallable, **kwargs)` in `internal/bot/common/bot.py`. Retries on `telegram.error.TimedOut`, base `telegram.error.NetworkError` (excludes `BadRequest`), `telegram.error.RetryAfter`. Exception order in the helper is CRITICAL: `BadRequest` (raise) → `RetryAfter` (honor `retry_after`) → `NetworkError` (catches TimedOut + base) — because `BadRequest` subclasses `NetworkError` in PTB 22.8. 3 attempts total, exponential backoff `0.5 * 2**attempt + uniform(0, 0.5)`, `RetryAfter` honored as int or timedelta capped at 60s. Module-level TypeVar `_TelegramSendReturnT`.
- 4 constants in `internal/bot/constants.py`: `TELEGRAM_SEND_MAX_ATTEMPTS=3`, `TELEGRAM_SEND_RETRY_DELAY_BASE=0.5`, `TELEGRAM_SEND_RETRY_JITTER=0.5`, `TELEGRAM_RETRY_AFTER_CAP_SECONDS=60.0` (all UPPER_CASE, typed, docstring'd — match this style for new constants).
- Wired into 6 sites: `_sendTelegramMessage` (send_photo markdown+fallback, send_message markdown+fallback) + `editMessage` (edit_message_reply_markup, edit_message_text). NOT wired into `send_media_group` (out of scope v1), error-notice send, or Max path (Max already retries at `MaxBotClient._makeRequest`).
- **Coordinated narrowed-except restructure (Gate-2 polish):** the two markdown-fallback sites (send_photo + send_message paths) were restructured into TWO separate try blocks: (a) `markdownToMarkdownV2(...)` conversion wrapped in a BROAD `except Exception` safety net (sets `messageTextParsed = None` on any failure, then `else:` proceeds); (b) the `_retryTelegramSend` send wrapped in ONLY `except telegram.error.BadRequest`. This is the load-bearing design: transient errors (already retried inside the helper) bubble past `except BadRequest` to the outer handler, while markdown-conversion errors (incl. unexpected renderer bugs / future `strict_mode=True` RuntimeErrors) still gracefully degrade to plaintext. The `send_media_group` markdown path KEEPS its broad `except Exception` (unchanged — out of scope). LESSON: a single broad `except` around conversion+send conflates two concerns; splitting them is the correct pattern when adding retry inside such a block.
- 14 tests in `TestTelegramSendRetry` (`tests/bot/common/test_bot.py`): direct helper unit tests (TimedOut retry/exhaust, BadRequest/Forbidden no-retry, RetryAfter int/timedelta/over-cap/exhaustion, NetworkError, first-attempt success) + integration (`sendMessage` markdown-path TimedOut-doesn't-trigger-fallback KEY regression, BadRequest-triggers-fallback preserved-behavior, photo retry, editMessage retry). Three fixtures (`_resetSingletons`, `mockCacheService`, `telegramBot`) are MODULE-SCOPE (hoisted from `TestGetChatAdminsRegression` during this work — both classes share them).
- CHANGELOG `## [Unreleased]` → `### Added` one-liner. `TODO.md` checkbox for "retry to send message on telegram.error.TimedOut" marked done.

**Idempotency stance (user decision):** accepted the duplicate-message risk from `TimedOut` retries (a TimedOut may mean the message WAS delivered but the HTTP response was lost — retry can duplicate). Mitigated by capping at 3 attempts, not retrying `send_media_group`.

**Reusable facts for future work:**
- `markdownToMarkdownV2` (default `strict_mode=False`) does NOT raise `ValueError` on formatting issues — the parser catches internally and returns an error document. Only raises `ValueError` for non-`MDDocument` root (unreachable via `parse()`). In `strict_mode=True` it raises `RuntimeError`. So broad `except Exception` around the conversion is the right safety net.
- PTB v22.8 `RetryAfter.retry_after` is `int | timedelta`; a `PTBDeprecationWarning` is emitted for the int form (future timedelta-only). Code handles both via `isinstance` check — forward-compatible.
- `AsyncMock(spec=telegram.ext.ExtBot)` is the standard `tgBot` mock in tests. Raise-then-succeed pattern: `AsyncMock(side_effect=[TimedOut, success])`. Patch `asyncio.sleep` via `@patch("internal.bot.common.bot.asyncio.sleep", new_callable=AsyncMock)`.
