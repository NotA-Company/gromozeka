### Spike-verified pip --target behavior

- **pip `--target` behavior — SPIKE-VERIFIED FACTS (pip 26.2.1, 2026-09-04, temp-dir experiments; logs summarized in plans doc):**
  1. **NO satisfaction check under `--target` AT ALL** — every invocation re-resolves + re-downloads ("Requirement already satisfied" never appears; not against target, not against venv, not with exact pin, not with/without `--upgrade`). The "zero download when current" property is OURS to build, never pip's.
  2. **`--target --upgrade` wholesale-replaces colliding TOP-LEVEL DIRECTORIES**: upgrading protobuf deleted 196 googleapis-common-protos files (shared `google/` namespace), orphaned its dist-info, left stale duplicate protobuf dist-info. No `Attempting uninstall`, no RECORD cleanup.
  3. **`--target` WITHOUT `--upgrade` is also broken**: warns "Target directory … already exists. Specify --upgrade to force replacement", SKIPS code replacement but STILL writes the new dist-info → lying metadata + duplicate dist-info + stale code. **⇒ TODAY'S `/sandbox install` of an already-present package already corrupts the pool** (pre-existing production bug, exposed by the spike).
  4. `PYTHONPATH` is IGNORED for `--target` resolution (staging+PYTHONPATH does not restore satisfied-skips).
  5. `pip install --dry-run --report <file> --target <scratch>` IS non-mutating and usable as an outdated-oracle: report `install[]` gives resolved versions to compare against pool dist-infos — the correct way to get "skip download when current".
### Ratified rev-2 mechanism and lock placement

- **Mechanism consequence (rev 2 RATIFIED 2026-09-04, user-approved):** pip NEVER writes into the live pool. Flow: dry-run-report pre-filter (outdated subset + `upToDate` skip set) → poolLock → host-side copytree pool→`<root>/tmp/<runId>/newpool` → stage container `pip install --target <staging>/delta` (pool NOT mounted) → host-side merge (full-RECORD delete of old dist-infos + copytree overlay; NO set-subtraction) → atomic double-rename swap (inline rollback; crash window adopted by `recover()`: adopt `newpool` ONLY when sibling `oldpool` ALSO exists — both-present proves the swap began ⇒ merge was complete; newpool-only run dirs are uncommitted staging garbage for GC, never adopted; oldpool-only restores) → refresh + diff. Helper renamed `pool_pip_runner.py` (two modes: `--report <file>` / `--install-into <dir>`, `--` before specs); host-side `pool_staging.py` absorbs the parser/jail/merge/swap logic. Install path unified onto the same core in Phase 1I (fixes the pre-existing install bug; `upgrade=` becomes documented no-op; `installCommand` deleted then).
- **Lock placement — CORRECTED premise:** the flock file ALREADY lives at `<runtimes/python>/pool.lock` — a SIBLING of the swapped `libs/` dir (locks.py:294, poolDir=`<root>/runtimes/python` from manager.py:949/1098). NO relocation needed; revision 2 pins it as an invariant (regression test: lock path outside `libs/`; never swap the whole runtime dir).
