# LLM Tool-Call Healing (internal/services/llm/service.py) — implemented 2026-07-15

Archived durable notes from [`../teamlead-memory.md`](../teamlead-memory.md) (extracted 2026-07-18). See the live compact memory there for cross-cutting rules and workflow lessons.

`generateTextViaLLM` runs a `while True` loop: `generateText` → if `status==FINAL and resultText`, try to HEAL embedded tool calls; if `status==TOOL_CALLS`, execute tools, append assistant+tool messages, loop; else break. **Post-budget gate** (`roundN >= maxRounds`, added 2026-07-16, see [`use-tools-filtering.md`](use-tools-filtering.md) and [`llm-max-rounds.md`](llm-max-rounds.md)): both the FINAL heal branch AND the TOOL_CALLS execute branch are gated on `not budgetExhausted` (service.py:858, 870), so post-budget healing cannot re-arm execution the cap just disabled; FINAL text past the cap is treated as truly final.

- **Healing matchers** (each mutates `ModelRunResult` in-place to `TOOL_CALLS`, returns bool): `_matchTextForJSONToolCall` (``` ```json{...}``` ``` fences; since 2026-07-19 also accepts `"function"` key as fallback when `"name"` is absent or empty), `_matchTextForToolCallTags` (`<tool_call>{json}</tool_call>`), `_matchTextForToolCallStart` (`[TOOL_CALL_START] name{json}`), `_matchTextForToolCallSquareBracketsAndJson` (`[name]\n{json}`, name must be `\S+`), and `_matchTextForInlineCodeToolNameAndJson` (the entire response is `` `name` `` plus a fenced JSON argument object; rejects unknown tools, malformed JSON, and any parsed trailing content). Shared tail: `_tryApplyToolCallMatch(mlRunResult, *, toolName, parameters, toolCallId, prefixStr, suffixStr)` — accepts match only when `(not prefixStr or not suffixStr)` (begin/end edge) AND `toolName` truthy AND `toolName in self.toolsHandlers` AND `isinstance(parameters, dict)`. **Note:** healing accepts on the GLOBAL `toolsHandlers` registry, NOT the per-call `filteredToolNames` allowlist — but the execution loop re-guards on `filteredToolNames`, so a `useTools`-filtered tool gets healed→"not available" error, never executes (see `use-tools-filtering.md`). JSON parse helper: `_tryParseJson(data)` (raw_decode + `\'` fix fallback).
- **Orchestrator `_tryHealToolCall(mlRunResult) -> bool`** runs all strategies in priority order: JSON-fence → `_matchTextForToolCallTags` (`<tool_call>{json}</tool_call>`, e.g. YC aliceai-llm emits this; JSON shape `{name, arguments}`, `{name, parameters}`, or `{function, arguments}`; since 2026-07-19 also accepts `"function"` key as fallback when `"name"` is absent or empty) → TOOL_CALL_START → `[name]{json}` → inline-code `name` + fenced JSON arguments → `_matchTextForBrokenKnownToolCall` (last-resort fallback).
- **Broken-known-tool fallback** `_matchTextForBrokenKnownToolCall`: last-resort matcher for UNPARSEABLE calls that nonetheless reference a registered tool name inside a bracket block `[...]`. Rewritten 2026-07-19 to fix two root-cause bugs that blocked healing of the 0719 capture (see corpus below). **Old (buggy) shape:** single `re.match` with non-greedy `(.*?)` anchored at start of text, requiring the bracket to be at an edge (`if prefixStr.strip() and suffixStr.strip(): return False`). Two failure modes: (1) **wrong-bracket matching** — the non-greedy `(.*?)` stopped at the FIRST `[` in the text, which in the 0719 case was a markdown link label `[label]`\(url\) (e.g. `[Новостный сайт]`\(https://news.ru/...\)) rather than the actual broken-call bracket `[Вызов функции \`generate_and_send_image\`]` later in the text — the relevant bracket was never reached; (2) **edge constraint too strict** — even if the right bracket were matched, the at-edge check rejected it because the bracket was mid-message (article prose before, fenced JSON params block after). **New shape:** `re.finditer(r"\[(.+?)\]", resultText, re.DOTALL)` scans ALL `[...]` blocks in text order; for each bracket, the tool name is searched via word-boundary regex `(?<![\w]){escapedName}(?![\w])` (unchanged) inside the bracket content only. Acceptance rule replaced at-edge-only with `atEdge OR hasJsonParams`: (a) **atEdge** — empty/whitespace-only prefix OR suffix, AFTER stripping surrounding triple-backticks (`prefixStr.strip().strip("`").strip()`), preserving the legacy ` ```\n[name]\n``` ` edge shape; (b) **hasJsonParams (replaces former `inBackticks`)** — the entire suffix after the bracket is an optional fenced JSON code block: `re.match(r"^\s*`*(json)?\s*{.*}\s*`*\s*$", suffixStr, re.DOTALL)`. This captures the structural shape "broken-call bracket immediately followed by its would-be parameters block" — a fingerprint of a model attempting a tool call that real prose mentions don't produce. The JSON-params-suffix signal is more robust than the previous `inBackticks` signal because it doesn't depend on the bracket using backtick syntax for the tool name. An accepted one-round-trip false positive is possible if prose happens to end in `[registered_tool_name]` followed by a standalone JSON code block, but this is rare in practice. First matching bracket (in text order) wins. On match: mutates `mlRunResult` to `TOOL_CALLS`, preserves the matched bracket in `resultText` (model sees its full original intent on retry), synthesises one `LLMToolCall` with empty `parameters={}` and `errorMessage=f"Found broken call of tool '{name}', retry with proper tool call"` (UNCHANGED from before — still emits a retry-error, never executes the handler). Deliberate narrowing: only `bracketContent` is searched for the tool name (OLD code searched `bracketContent + " " + bracesContent`); `[name]{json}` with name-only-in-JSON is left to the sibling matcher `_matchTextForToolCallSquareBracketsAndJson`. Accepted false-positive trade-off: a bare trailing markdown link `[toolName]`\(url\) as the whole/trailing response still matches via atEdge (documented in test `testBrokenKnownToolCallAcceptsTrailingMarkdownLink`).
- **`LLMToolCall.errorMessage`** (Optional[str]=None, `lib/ai/models.py`): internal-only plumbing — NOT in `__str__`, NOT serialized to API (`ModelMessage.toDict`, basic_openai_provider, yc_sdk_provider all read only `.id/.name/.parameters`). In the execution loop, `if toolCall.errorMessage is not None:` short-circuits BEFORE calling the handler → returns `{"done": False, "error": toolCall.errorMessage}` as a tool-result message so the model retries (mirrors the existing "tool not available" path). Wording: `f"Found broken call of tool '{name}', retry with proper tool call"`.
- **`processIntermediateMessages` gate** (`internal/bot/common/handlers/llm_messages.py`): when the result contains a tool call with `errorMessage` set, intermediate messages are suppressed (`return` early) so the model's internal retry prose is never sent to the user. The model sees the full original bracket text on retry (for context accuracy), but the user sees nothing — the broken-call noise stays invisible.
- **CONSUMER-AUDIT GOTCHA (Gate 2 caught this):** when adding an internal flag like `errorMessage` to a model object that flows through `toolUsageHistory`, audit ALL consumers that count/aggregate tool calls. `_countRefinementToolCalls` in `internal/bot/common/handlers/user_memories.py` (~L1380, two branches: `toolUsageHistory` walk + `result.toolCalls` fallback) feeds `addCount`/`deleteCount`/`searchCount` to `_writeRefinementJsonLog` (observability JSONL only — no behavioural decision reads it). It had to be updated to skip `errorMessage` calls (else a broken-then-retried tool double-counts). Lesson: a synthesised/never-executed marker must be excluded from usage metrics everywhere.
