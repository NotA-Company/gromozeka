# LLM Tool-Call Healing (internal/services/llm/service.py) — implemented 2026-07-15

Archived durable notes from [`../teamlead-memory.md`](../teamlead-memory.md) (extracted 2026-07-18). See the live compact memory there for cross-cutting rules and workflow lessons.

`generateTextViaLLM` runs a `while True` loop: `generateText` → if `status==FINAL and resultText`, try to HEAL embedded tool calls; if `status==TOOL_CALLS`, execute tools, append assistant+tool messages, loop; else break. **Post-budget gate** (`roundN >= maxRounds`, added 2026-07-16, see [`use-tools-filtering.md`](use-tools-filtering.md) and [`llm-max-rounds.md`](llm-max-rounds.md)): both the FINAL heal branch AND the TOOL_CALLS execute branch are gated on `not budgetExhausted` (service.py:858, 870), so post-budget healing cannot re-arm execution the cap just disabled; FINAL text past the cap is treated as truly final.

- **Healing matchers** (each mutates `ModelRunResult` in-place to `TOOL_CALLS`, returns bool): `_matchTextForJSONToolCall` (``` ```json{...}``` ``` fences), `_matchTextForToolCallTags` (`<tool_call>{json}</tool_call>`), `_matchTextForToolCallStart` (`[TOOL_CALL_START] name{json}`), `_matchTextForToolCallSquareBracketsAndJson` (`[name]\n{json}`, name must be `\S+`). Shared tail: `_tryApplyToolCallMatch(mlRunResult, *, toolName, parameters, toolCallId, prefixStr, suffixStr)` — accepts match only when `(not prefixStr or not suffixStr)` (begin/end edge) AND `toolName` truthy AND `toolName in self.toolsHandlers` AND `isinstance(parameters, dict)`. **Note:** healing accepts on the GLOBAL `toolsHandlers` registry, NOT the per-call `filteredToolNames` allowlist — but the execution loop re-guards on `filteredToolNames`, so a `useTools`-filtered tool gets healed→"not available" error, never executes (see `use-tools-filtering.md`). JSON parse helper: `_tryParseJson(data)` (raw_decode + `\'` fix fallback).
- **Orchestrator `_tryHealToolCall(mlRunResult) -> bool`** runs all strategies in priority order: JSON-fence → `_matchTextForToolCallTags` (`<tool_call>{json}</tool_call>`, e.g. YC aliceai-llm emits this; JSON shape `{name, arguments}` or `{name, parameters}`) → TOOL_CALL_START → `[name]{json}` → `_matchTextForBrokenKnownToolCall` (last-resort fallback).
- **Broken-known-tool fallback** `_matchTextForBrokenKnownToolCall`: for UNPARSEABLE calls that nonetheless reference a registered tool name inside a bracket block `[...]` (any content, incl. spaces) / `[...]{...}` / optionally code-fenced, at BEGIN or END of message (prefix or suffix empty). Real examples (failed.2026-07-03.jsonl, failed.2026-07-10.jsonl): `[Вызов функции \`generate_and_send_image\` с промтом: «...»]`. Detection heuristic (user-confirmed): bracket-at-edge containing a known tool name → NOT a prose mention; word-boundary search `(?<![\w])name(?![\w])` (handles underscore names; `\w` includes `_`). Synthesizes `TOOL_CALLS` with the known name + empty params, sets `LLMToolCall.errorMessage`, strips bracket from resultText. Accepted false-positive trade-off: a bare trailing markdown link `[toolName](url)` as the whole/trailing response also matches (documented in test `testBrokenKnownToolCallAcceptsTrailingMarkdownLink`).
- **`LLMToolCall.errorMessage`** (Optional[str]=None, `lib/ai/models.py`): internal-only plumbing — NOT in `__str__`, NOT serialized to API (`ModelMessage.toDict`, basic_openai_provider, yc_sdk_provider all read only `.id/.name/.parameters`). In the execution loop, `if toolCall.errorMessage is not None:` short-circuits BEFORE calling the handler → returns `{"done": False, "error": toolCall.errorMessage}` as a tool-result message so the model retries (mirrors the existing "tool not available" path). Wording: `f"Found broken call of tool '{name}', retry with proper tool call"`.
- **CONSUMER-AUDIT GOTCHA (Gate 2 caught this):** when adding an internal flag like `errorMessage` to a model object that flows through `toolUsageHistory`, audit ALL consumers that count/aggregate tool calls. `_countRefinementToolCalls` in `internal/bot/common/handlers/user_memories.py` (~L1380, two branches: `toolUsageHistory` walk + `result.toolCalls` fallback) feeds `addCount`/`deleteCount`/`searchCount` to `_writeRefinementJsonLog` (observability JSONL only — no behavioural decision reads it). It had to be updated to skip `errorMessage` calls (else a broken-then-retried tool double-counts). Lesson: a synthesised/never-executed marker must be excluded from usage metrics everywhere.
